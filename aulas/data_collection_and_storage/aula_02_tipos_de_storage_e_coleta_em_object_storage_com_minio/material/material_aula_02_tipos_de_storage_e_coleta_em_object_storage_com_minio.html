2. Coleta e armazenamento como decisão arquitetural

Um script que chama uma API e salva a resposta em disco parece uma tarefa pequena. A dificuldade aparece semanas depois, quando alguém pergunta o que a previsão dizia para Manaus às 10h de uma terça-feira, ou por que existem duas versões do mesmo dado, ou quanto o armazenamento vai custar no fim do semestre. As respostas dependem de decisões tomadas no primeiro dia: onde o dado fica, com que nome, em que formato, com que informações sobre sua origem e o que acontece quando o coletor roda duas vezes.

Essas decisões são arquiteturais no sentido usado na Aula 01: são caras de mudar depois, afetam atributos de qualidade (confiabilidade, rastreabilidade, custo, segurança) e precisam ser justificadas por requisitos. Trocar o formato de chave de um bucket com milhões de objetos exige reescrever todos eles. Gravar sem metadados de coleta torna impossível, depois, separar um dado correto de um dado coletado por uma versão defeituosa do coletor.

Por isso a aula começa pelos tipos de armazenamento. O object storage é a escolha da camada bruta nesta disciplina, mas essa escolha só fica defensável quando comparada com as alternativas e com os trabalhos que cada uma faz bem.

3. Tipos de storage e seus trade-offs

A comparação abaixo organiza os tipos pela unidade que o cliente lê e escreve. Essa unidade determina o protocolo, a forma de atualizar um pedaço do dado e o tipo de escala que o sistema suporta.

3.1 Block storage

O armazenamento em bloco expõe ao sistema operacional um dispositivo dividido em blocos de tamanho fixo, endereçados por número. O disco do notebook, um SSD NVMe e os volumes de nuvem anexados a uma máquina virtual são exemplos. O dispositivo não sabe o que é um arquivo: quem organiza os blocos em arquivos e diretórios é o sistema de arquivos instalado por cima (ext4, XFS, NTFS), ou o próprio banco de dados quando ele gerencia páginas diretamente.

A vantagem é a latência baixa e a atualização parcial: um banco de dados reescreve uma página de 8 KB sem tocar no resto do arquivo. A limitação é o acoplamento. Em geral um volume em bloco é montado por uma máquina por vez, e crescer significa redimensionar o volume e o sistema de arquivos. O volume que o Railway monta em /data no serviço do MinIO é armazenamento desse tipo: o MinIO grava ali e oferece objetos para fora.

3.2 File storage: sistemas de arquivos locais e em rede

O armazenamento em arquivo oferece a hierarquia de diretórios e arquivos que todo programador conhece, com operações POSIX como abrir, ler a partir de um deslocamento, acrescentar ao final, renomear e travar. Localmente, é o sistema de arquivos sobre um disco em bloco. Em rede, protocolos como NFS (comum em Linux) e SMB (comum em ambientes Windows) permitem que várias máquinas montem o mesmo diretório compartilhado.

O modelo é familiar e aceita atualização parcial, o que o torna adequado para pastas compartilhadas, diretórios de trabalho de ferramentas que esperam caminhos locais e aplicações legadas. Os custos aparecem na escala: manter a semântica de diretório (renomear uma pasta, listar, travar arquivos) entre muitos clientes exige coordenação, e a hierarquia vira gargalo quando milhões de arquivos ficam no mesmo diretório.

3.3 Object storage

O armazenamento de objetos guarda cada dado como um objeto inteiro dentro de um bucket, identificado por uma chave textual e acompanhado de metadados. O acesso é feito por HTTP, com operações como PUT, GET, HEAD, DELETE e listagem por prefixo. Não existe diretório de verdade: a barra em open_meteo/data=2026-10-17/sao_paulo.json é só um caractere da chave, que as ferramentas exibem como pasta. O objeto também não aceita atualização parcial: para mudar um byte, regrava-se o objeto inteiro.

Essas restrições permitem escalar a capacidade quase sem limite prático e a um custo por gigabyte menor que o de bloco e arquivo, já que o sistema não precisa coordenar travas nem hierarquia. A API do S3 virou o padrão de fato para object storage: MinIO, Ceph, Cloudflare R2 e outros implementam uma API compatível com S3, e bibliotecas como boto3, ferramentas como DuckDB e Spark e o cliente mc falam com qualquer um deles mudando apenas o endpoint. É por isso que o MinIO serve à disciplina: o código escrito contra ele roda contra outro provedor compatível sem reescrita.

3.4 Bancos relacionais

O banco relacional (PostgreSQL, MySQL, SQLite) organiza o dado em tabelas com esquema declarado, chaves e restrições, e oferece SQL e transações ACID. Ele faz bem o que o object storage não faz: atualizar uma linha, garantir que duas operações aconteçam juntas ou nenhuma aconteça, impedir que um pedido aponte para um cliente inexistente. Paga por isso com esquema rígido na escrita (o dado precisa caber na tabela antes de entrar) e com escala horizontal mais difícil. Para guardar a resposta bruta de uma API cujo formato pode mudar, o esquema rígido trabalha contra: um campo novo exige migração antes da coleta. O relacional volta na Aula 05, onde o problema é justamente modelar.

3.5 Chave-valor e documento

Bancos chave-valor (Redis, Valkey, etcd) devolvem um valor a partir de uma chave com latência muito baixa, e servem a cache, sessão, contadores e filas leves. Bancos de documento (MongoDB, Couchbase) guardam documentos JSON com esquema flexível e permitem consultar por campos internos. Ambos aceitam atualização de um registro e escalam particionando por chave. O limite é a consulta analítica ampla: agregar um campo sobre milhões de documentos não é o trabalho para o qual foram desenhados. Um banco de documento poderia receber o JSON da Open-Meteo, mas cobraria por um recurso (consulta por campo e atualização) que a camada bruta não usa.

3.6 Colunar e analítico

Armazenamentos colunares (ClickHouse, DuckDB, data warehouses, e formatos de arquivo como Parquet) guardam os valores de uma mesma coluna juntos. Uma consulta que soma uma coluna lê só aquela coluna e se beneficia de compressão alta, já que valores parecidos ficam vizinhos. O preço está na escrita: inserir linha a linha é caro, atualizar um registro isolado é caro, e o esquema precisa ser conhecido. Por isso esses sistemas costumam ler de uma camada bruta e não substituí-la. A Aula 04 transforma o JSON gravado hoje em Parquet e consulta com DuckDB; a Aula 06 usa ClickHouse para leituras de sensores.

3.8 Como escolher

A tabela não aponta um vencedor; ela descreve trabalhos diferentes. Para escolher, cinco perguntas costumam bastar:

  1. Qual é a unidade natural do dado? Uma resposta inteira de API, uma linha de pedido ou um valor de cache.
  2. O dado será atualizado em pedaços ou só gravado e lido? Dados brutos de coleta são gravados uma vez e lidos muitas.
  3. Quem lê, com que padrão? Um analista agregando colunas, uma aplicação buscando por chave ou um job reprocessando tudo.
  4. O formato pode mudar sem aviso? Se sim, esquema rígido na escrita obriga a parar a coleta para migrar.
  5. Quanto vai crescer e quem paga? O custo por gigabyte e o custo por requisição pesam diferente conforme o volume.

Para a resposta bruta de uma API pública coletada a cada hora, as respostas apontam para o object storage: unidade natural é o documento inteiro, não há atualização parcial, a leitura será em lote pelas próximas aulas, o formato pode mudar e o volume cresce continuamente.

4. Object storage por dentro

4.1 Bucket, chave e objeto

O bucket é o contêiner de nível mais alto: tem nome único no servidor e é onde se aplicam políticas de acesso, versionamento e ciclo de vida. Dentro dele, cada objeto é endereçado por uma chave, que é uma string. A listagem aceita um prefixo e um delimitador, e é isso que permite navegar como se houvesse pastas: listar com prefixo open_meteo/data=2026-10-17/ devolve só os objetos daquele dia. A consequência prática é que o desenho da chave define quais leituras serão baratas. Ler um dia inteiro é uma listagem por prefixo; ler uma cidade em todos os dias, com a chave proposta nesta aula, exige listar todos os dias.

4.2 Metadados

Cada objeto carrega metadados do sistema (tamanho, data de modificação, ETag, tipo de conteúdo) e metadados definidos pelo usuário, enviados como cabeçalhos x-amz-meta-* na gravação. Os metadados de usuário são lidos com uma operação HEAD, sem baixar o conteúdo, o que os torna úteis para guardar a origem do dado. Duas restrições importam: os valores trafegam em cabeçalhos HTTP, então devem ficar em ASCII (escreva sao_paulo, não São Paulo), e o conjunto tem tamanho limitado, então guarde informação de procedência, não o dado.

4.3 Imutabilidade do objeto

Um objeto não é editado no lugar. Uma nova gravação na mesma chave substitui o objeto inteiro, ou cria uma nova versão quando o versionamento está ligado. Essa propriedade combina com a camada bruta: o que foi coletado fica como foi coletado, e qualquer correção é um objeto novo ou uma transformação em outra camada.

4.4 Consistência

Consistência responde à pergunta: depois que uma gravação foi confirmada, uma leitura logo em seguida vê o dado novo? A documentação do MinIO declara consistência estrita de leitura após escrita e de listagem após escrita, tanto em modo distribuído quanto em modo de um nó, com uma condição: a garantia vale para sistemas de arquivos como XFS, ZFS e Btrfs, e a mesma página desaconselha ext4. O sistema de arquivos do volume do Railway não foi verificado para esta aula, o que torna a premissa uma hipótese a registrar no ATAM. Outros sistemas compatíveis com S3 podem oferecer garantias diferentes: a garantia pertence ao servidor, e a API compatível não a transfere. Para o coletor, isso significa que um HEAD logo após um PUT confirmado encontra o objeto, o que sustenta a verificação de existência usada na idempotência.

4.5 API compatível com S3

O cliente fala com o MinIO exatamente como falaria com outro serviço compatível, mudando o endpoint. Em Python, com boto3, isso se faz com endpoint_url. Dois detalhes evitam horas de depuração: use endereçamento por caminho (Config(s3={"addressing_style": "path"})), porque o domínio do Railway não resolve subdomínios por bucket; e informe uma região (o MinIO aceita us-east-1 como padrão), porque a assinatura das requisições a exige.

4.6 Versionamento

Com o versionamento ligado no bucket, cada gravação na mesma chave cria uma versão nova e preserva as anteriores, e uma exclusão apenas marca o objeto como apagado. O benefício é recuperar dados sobrescritos por engano. O custo é armazenamento: cada versão ocupa espaço. Na preparação desta aula, o versionamento foi ligado num MinIO local com a mesma imagem usada pelo grupo (mc version enable) e duas gravações na mesma chave produziram duas versões listadas por mc ls --versions. Nesta aula, o versionamento funciona também como detector: se a contagem de versões cresce quando o coletor roda duas vezes na mesma hora, a idempotência falhou.

4.7 Ciclo de vida

Regras de ciclo de vida (lifecycle, ou ILM no MinIO) expiram objetos ou versões antigas automaticamente após um número de dias, por prefixo. Exemplo testado na preparação: mc ilm rule add --noncurrent-expire-days 7 local/raw apaga versões não correntes após sete dias. A regra transforma o crescimento do bucket numa decisão explícita, e não num efeito colateral descoberto quando o crédito do Railway acaba.

5. Desenho da camada raw: chaves, formatos, imutabilidade e idempotência

5.1 Prefixos e particionamento no estilo Hive

A convenção de particionamento popularizada pelo Hive escreve cada nível da chave como nome=valor. Assim, open_meteo/data=2026-10-17/hora=12/sao_paulo.json diz, só pela chave, que o objeto veio da Open-Meteo, foi coletado em 17/10/2026 às 12h e se refere a São Paulo. Ferramentas como DuckDB e Spark reconhecem esse padrão e transformam data e hora em colunas, o que a Aula 04 usará para ler só as partições de interesse. A chave adotada nesta aula é:

bucket: raw
chave:  open_meteo/data=AAAA-MM-DD/hora=HH/<cidade>.json
exemplo: open_meteo/data=2026-10-17/hora=12/sao_paulo.json

Três decisões estão embutidas nessa chave e devem aparecer no ADR do grupo. A partição é pelo momento da coleta, e não pelo horário previsto, porque cada resposta contém previsões para várias horas. O fuso da partição precisa ser fixado (a proposta da aula é UTC, que não sofre mudança de horário; o fuso local fica nos metadados). E o nome da cidade vira um identificador ASCII sem espaços, estável ao longo do tempo.

5.2 Formatos brutos: JSON e JSON Lines

JSON guarda um documento por arquivo e preserva a resposta exatamente como a API a enviou. JSON Lines (JSONL) guarda um documento JSON por linha, o que permite acrescentar registros e ler em fluxo, linha a linha. Para a resposta da Open-Meteo, um objeto JSON por cidade e por hora preserva o documento original e mantém a chave determinística. O JSON Lines aparece no manifesto de execução: um arquivo por execução, com uma linha por cidade registrando o resultado (gravado, já existia, erro) e eventuais alertas, como uma resposta cuja forma mudou. Uma mudança de schema na fonte não impede a gravação na raw, que guarda o que chegou; ela vira um alerta para quem transforma o dado depois.

5.3 Imutabilidade da camada raw

A camada raw guarda o que a fonte entregou, sem limpeza, renomeação de campos ou conversão de unidades. Se uma transformação estiver errada, a camada raw permite refazê-la; se a raw tiver sido transformada, o original se perdeu. Por isso o coletor grava os bytes recebidos e coloca as informações de procedência nos metadados do objeto, sem embrulhar a resposta num envelope que altere o documento.

5.4 Idempotência na escrita

Uma operação é idempotente quando executá-la duas vezes produz o mesmo estado que executá-la uma vez. Coletores são reexecutados por muitos motivos: agendador que dispara de novo, pessoa que roda à mão para testar, retry depois de erro de rede. Se cada execução gerasse uma chave nova (por exemplo, com o horário em segundos ou um UUID), cada repetição duplicaria dados. A chave determinística resolve: a mesma cidade, na mesma hora de coleta, sempre produz a mesma chave. A política proposta é "a primeira gravação da hora vale": antes de gravar, o coletor faz HEAD na chave; se o objeto existe, não grava e registra ja_existia no manifesto.

A lição do projeto ClickHouse no Railway, do professor, mostra por que isso importa: o proxy do Railway devolve 502 de forma esporádica. Com retry e chave determinística, repetir a gravação é seguro. Sem chave determinística, o retry de uma gravação que de fato chegou ao servidor, mas cuja confirmação se perdeu, cria um duplicado.

Fica um risco residual, que deve entrar no ATAM: duas execuções simultâneas podem fazer o HEAD ao mesmo tempo, não encontrar o objeto e gravar as duas. Com versionamento ligado, isso aparece como duas versões. Para um coletor horário com uma execução por vez, o risco é baixo; para um coletor com várias réplicas, exigiria trava ou gravação condicional.

6. A fonte da aula: API de previsão da Open-Meteo

A Open-Meteo oferece uma API de previsão do tempo sem chave de acesso para uso não comercial. O endpoint é https://api.open-meteo.com/v1/forecast. Os parâmetros usados na aula, conferidos na documentação e numa chamada real em 03/10/2026:

ParâmetroValor na aulaObservação
latitude, longitudecoordenadas da capitalobrigatórios; aceitam várias coordenadas separadas por vírgula, caso em que a resposta vira uma lista
hourlytemperature_2m,relative_humidity_2mvariáveis horárias; há dezenas de outras, como precipitation e wind_speed_10m
timezoneAmerica/Sao_Paulopadrão é GMT; auto resolve pelo local
forecast_days1de 0 a 16; padrão 7

A resposta traz no nível superior latitude, longitude, generationtime_ms, utc_offset_seconds, timezone, timezone_abbreviation, elevation, hourly_units e hourly; este último contém a lista time e uma lista por variável pedida. Um parâmetro inválido devolve HTTP 400 com o corpo {"error": true, "reason": "..."}.

curl -s "https://api.open-meteo.com/v1/forecast?latitude=-23.55&longitude=-46.63&hourly=temperature_2m,relative_humidity_2m&timezone=America/Sao_Paulo&forecast_days=1" | python -m json.tool | head -30

curl -s -w "\nHTTP %{http_code}\n" "https://api.open-meteo.com/v1/forecast?latitude=-23.55&longitude=-46.63&hourly=temperatura"

Na mesma verificação, a resposta para uma cidade com forecast_days=1 e duas variáveis teve 989 bytes; com forecast_days=7, 4.877 bytes. São medidas de uma chamada, úteis para estimar ordem de grandeza do crescimento do bucket, e não um tamanho garantido.

Os termos de uso limitam o uso gratuito não comercial a menos de 10.000 chamadas por dia, 5.000 por hora e 600 por minuto, e exigem a aceitação da licença CC BY 4.0, que pede atribuição da fonte. Seis capitais coletadas a cada hora somam 144 chamadas por dia, bem abaixo do limite.

Por que guardar a resposta toda hora? Porque o endpoint devolve a previsão vigente no momento da chamada. Quem quiser saber, depois, o que a previsão dizia às 10h de um dia precisa ter gravado a resposta às 10h daquele dia. A camada raw é esse registro.

A edição comunitária do MinIO entrou em modo de manutenção e deixou de ter imagens Docker oficiais publicadas; a imagem da coolLabs é construída a partir das releases oficiais. A tag fica fixa para que todos rodem a mesma versão. Um segundo serviço, minio-init, espera o MinIO ficar saudável e cria o bucket raw.

cp .env.example .env
SENHA=$(openssl rand -base64 24)
sed -i "s|^MINIO_ROOT_PASSWORD=.*|MINIO_ROOT_PASSWORD=$SENHA|; s|^S3_SECRET_KEY=.*|S3_SECRET_KEY=$SENHA|" .env
unset SENHA

docker compose config -q && echo "compose ok"
docker compose up -d
docker compose ps -a
docker compose logs minio-init

Gate: minio aparece como healthy, minio-init termina com Exited (0) e git status não lista .env.

A imagem do MinIO já traz o cliente mc, então não é preciso instalá-lo. Registre um alias dentro do contêiner e ligue o versionamento:

docker compose exec minio mc version enable local/raw

8. O projeto da aula em SDD

O cenário a seguir é fictício e serve para dar ao agente um problema concreto. Uma distribuidora de bebidas opera centros de distribuição em seis capitais. A equipe de planejamento quer, mais adiante, comparar a previsão de temperatura e umidade com as vendas de bebidas geladas e ajustar o estoque de cada centro. Para isso, precisa de um histórico do que a previsão dizia a cada hora, guardado sem alteração, que as próximas etapas (Aula 04) vão transformar e consultar.

O projeto desta aula entrega só a primeira peça: o coletor e a camada raw. A sequência de prompts segue a convenção da disciplina:

Persona e objetivosPrompts 1 e 2: quem usa, que decisão toma, como medir sucesso.
EspecificaçãoPrompt 3: RF e RNF com Dado/Quando/Então.
Plano e tarefasPrompts 4 e 5: C4, módulos, tarefas ligadas a testes.
ImplementaçãoPrompt 6: uma tarefa por vez, teste antes de seguir.
ATAMPrompt 7: cenários, riscos, ADRs e evidências.

Todos os prompts carregam as mesmas regras: não inventar números nem SLAs (marcar "hipótese, validação pendente"), separar fato, lacuna e suposição, preservar os IDs de requisito, não pôr segredos em arquivo versionado, mostrar o plano antes de editar e parar ao fim da etapa. Copie cada prompt por inteiro. A revisão que vem depois de cada um é a parte que produz aprendizado: o agente erra, e o grupo precisa pegar o erro antes que ele contamine a etapa seguinte.

10. Execução e verificação no MinIO local

Com as tarefas implementadas e os testes passando, rode o coletor contra o MinIO local. O carregamento do .env com set -a exporta todas as variáveis para o processo Python.

set -a; source .env; set +a
python -m pytest -q
python -m src.coletor
python -m src.coletor   # segunda vez na mesma hora

Verifique o bucket com o mc dentro do contêiner. Quando a saída segue por um pipe (| wc -l, | sha256sum), use exec -T: sem terminal alocado, os bytes chegam ao comando seguinte sem conversão de fim de linha.

docker compose exec minio mc ls --recursive local/raw/open_meteo/
docker compose exec -T minio mc find local/raw/open_meteo --name "*.json" | wc -l
docker compose exec -T minio mc ls --recursive --versions local/raw/open_meteo/ | wc -l
docker compose exec minio mc ls --recursive local/raw/_manifestos/

Inspecione um objeto, trocando data, hora e cidade pelos valores da sua execução:

docker compose exec minio mc stat local/raw/open_meteo/data=2026-10-17/hora=12/sao_paulo.json
docker compose exec -T minio mc cat local/raw/open_meteo/data=2026-10-17/hora=12/sao_paulo.json | python -m json.tool | head -20
docker compose exec -T minio mc cat local/raw/open_meteo/data=2026-10-17/hora=12/sao_paulo.json | sha256sum
Gates locais
  • python -m pytest -q sem falhas.
  • Número de objetos .json igual a seis vezes o número de horas coletadas.
  • A segunda execução na mesma hora não muda a contagem de objetos nem a de versões, e o manifesto dela mostra ja_existia para as seis cidades.
  • mc stat mostra os metadados X-Amz-Meta-Fonte, X-Amz-Meta-Coletado-Em, X-Amz-Meta-Versao-Coletor, X-Amz-Meta-Sha256 e os de cidade e coordenada.
  • O sha256sum do conteúdo é igual ao metadado de hash.

Teste também a falha. Com o MinIO parado (docker compose stop minio), o coletor deve terminar com código diferente de zero, sem travar, depois de esgotar as tentativas definidas no spec. Confira com echo $? e suba de novo com docker compose start minio.

11. Execução contra o MinIO do Railway

O mesmo código roda contra o MinIO do Railway mudando só as variáveis de ambiente. Esse é o teste prático da escolha por uma API compatível com S3.

  1. Crie .env.railway a partir do .env e troque S3_ENDPOINT_URL pelo domínio público da porta 9000 (com https://), e S3_ACCESS_KEY e S3_SECRET_KEY pelas credenciais do MinIO do Railway. Confirme com git status --short que o arquivo não aparece.
  2. Registre o alias railway no mc sem passar as chaves na linha de comando. O mc pede os valores de forma interativa, e eles não ficam no histórico do shell.
  3. Garanta o bucket e o versionamento no Railway.
  4. Rode o coletor duas vezes e verifique contagens e tamanho.
cp .env .env.railway
# edite .env.railway com o endpoint e as credenciais do Railway
git status --short

docker compose exec minio mc alias set railway https://<dominio-da-porta-9000>
docker compose exec minio mc mb --ignore-existing railway/raw
docker compose exec minio mc version enable railway/raw

set -a; source .env.railway; set +a
python -m src.coletor
python -m src.coletor

docker compose exec minio mc ls --recursive railway/raw/open_meteo/
docker compose exec -T minio mc find railway/raw/open_meteo --name "*.json" | wc -l
docker compose exec -T minio mc ls --recursive --versions railway/raw/open_meteo/ | wc -l
docker compose exec minio mc du railway/raw

set -a; source .env; set +a   # volta ao ambiente local

Se o proxy do Railway devolver 502, os logs do coletor devem mostrar novas tentativas com espera crescente, e as contagens não podem crescer além do esperado. Guarde essa saída: ela é evidência do cenário C-03 no ATAM.

O mc du dá o tamanho do bucket. Com seis objetos por hora, são 144 objetos por dia; multiplicado pelo tamanho medido de cada objeto, o grupo tem uma estimativa de crescimento para o cenário C-04. O preço do volume no Railway deve ser consultado na página de preços da plataforma no dia da análise e citado com data. Lembre ainda que volumes de contas em teste são apagados 30 dias após o fim dos créditos: planeje a exportação dos dados ao fim da disciplina.

12. Exemplo resolvido: cenário, ADR e rastreabilidade

Este exemplo mostra o nível de detalhe esperado no docs/atam.md para um cenário. Os valores medidos devem vir da execução do grupo.

Cenário C-03: 502 do proxy do Railway no PUT

Fonte do estímuloproxy de entrada do Railway
Estímuloresposta 502 a um PUT de objeto
Ambientecoleta normal contra o MinIO do Railway
Artefatogravador do coletor e bucket raw
Respostao cliente repete a gravação com espera crescente; ao repetir, grava na mesma chave; se as tentativas se esgotarem, registra erro no manifesto e segue para a próxima cidade
Medidanenhuma versão extra em open_meteo/ além de uma por cidade e hora; código de saída diferente de zero quando houver erro final

Descobertas. Ponto de sensibilidade: o número de tentativas e a espera determinam se a coleta da hora termina dentro da própria hora. Trade-off: mais tentativas aumentam a chance de gravar, mas alongam a execução e consomem mais requisições. Risco: se o PUT chegou ao servidor e só a resposta se perdeu, a nova tentativa grava os mesmos bytes na mesma chave; com versionamento ligado, isso cria uma segunda versão idêntica. Não-risco: não há duplicação de chave, porque a chave é determinística.

ADR-002 resumido: primeira gravação da hora vale

  • Status: aceito.
  • Contexto: o coletor pode rodar mais de uma vez na mesma hora; a camada raw deve ser imutável.
  • Alternativas: última gravação vale (sobrescrever); chave com horário em segundos (sem idempotência); gravação condicional no servidor (depende de suporte a verificar).
  • Decisão: HEAD antes do PUT; se existir, não grava e registra ja_existia.
  • Consequências: positiva, reexecução segura e contagem estável; negativa, a previsão mais nova dentro da hora é descartada; risco residual em execuções simultâneas.
  • Requisitos: RF de idempotência e RF de chave determinística do spec do grupo.
  • Revisão: se o coletor passar a rodar em mais de uma réplica.

13. Erros comuns

  • Reserializar o JSON antes de gravar (json.dumps(response.json())). O conteúdo muda (espaços, ordem, escape) e o hash deixa de corresponder ao que a API enviou.
  • Usar o horário local na chave sem declarar o fuso. A partição fica ambígua se houver mudança de horário e não se alinha com o metadado em UTC.
  • Pôr acento nos metadados (São Paulo). Cabeçalhos HTTP esperam ASCII.
  • Esquecer o endereçamento por caminho no boto3. O cliente tenta resolver raw.<dominio> e falha com erro de DNS ou de certificado.
  • Repetir requisições que devolveram HTTP 400. O erro é do pedido; repetir só consome cota.
  • Testes unitários que chamam a API real ou o MinIO. Passam ou falham conforme a rede, e consomem cota.
  • Colar a senha do MinIO no prompt, no mc alias set com chaves na linha de comando ou num arquivo versionado. Se acontecer, troque a senha no Railway.
  • Pedir ao agente várias etapas num prompt só. Além de esgotar o limite diário da OpenRouter, o grupo perde o ponto de revisão entre as etapas.
