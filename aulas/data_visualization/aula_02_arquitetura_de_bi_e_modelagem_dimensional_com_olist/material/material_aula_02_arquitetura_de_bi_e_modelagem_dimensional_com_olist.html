Aula 02 — Arquitetura de BI e Modelagem Dimensional com Olist

Aula 02 · 22/08/2026 · Sábado · 8h30 – 12h10

1. Visão geral

Uma visualização confiável depende da arquitetura que movimenta os dados, do modelo que organiza seu significado e das regras que preservam a granularidade das medidas. Esta aula examina esses três elementos de forma integrada. A primeira parte localiza fontes, transformações, persistência, camada semântica e artefatos nas arquiteturas do Power BI, do Grafana e do Metabase. A segunda parte converte o esquema relacional do Olist em um modelo dimensional voltado para consumo analítico.

O laboratório utiliza o banco Olist hospedado no Railway e conectado à instância Metabase da disciplina. A conexão analítica possui permissão de leitura. Dimensões e fatos serão implementados como consultas SQL salvas e reutilizados por referência no editor do Metabase. Para relacionar a atividade a um ambiente de engenharia de dados, cada consulta também poderá ser materializada como VIEW em um warehouse com permissão de escrita; essa variante aparece no material como referência de implantação.

Resultados esperados

  • explicar o percurso dos dados em Power BI Desktop, Power BI Service, Power BI Report Server, Grafana e Metabase;
  • distinguir dados analíticos, estado da aplicação, modelo semântico, cache e artefatos de consumo;
  • relacionar Data Warehouse, data mart, data lake, lakehouse e data mesh sem tratá-los como sinônimos;
  • declarar processo de negócio, grão, medidas, dimensões e chaves antes de escrever a consulta;
  • construir uma dimensão data, uma dimensão cliente SCD Tipo 2, dimensões de produto e vendedor e um fato no grão de item;
  • comparar esquema estrela e snowflake e justificar a escolha adotada;
  • identificar fanout em junções entre fatos, construir uma grade com CROSS JOIN e executar drill-across;
  • utilizar metadados do esquema em uma interação controlada com IA para propor uma extensão do modelo;
  • validar unicidade, integridade, reconciliação e cardinalidade.

4. Anatomia de uma arquitetura de BI

Uma arquitetura de BI pode ser analisada por cinco responsabilidades. As fontes registram eventos operacionais; mecanismos de movimentação conectam e transformam os dados; a camada de persistência mantém conjuntos preparados para análise; a camada semântica acrescenta relações, medidas, nomes de negócio e políticas; a camada de consumo entrega relatórios, painéis, alertas e exploração.

Ferramentas comerciais e open source distribuem essas responsabilidades de maneiras diferentes. A comparação técnica começa com quatro perguntas:

  1. Onde estão os dados usados pelo visual? Eles podem permanecer na fonte, ser importados para um modelo ou ser armazenados em cache.
  2. Onde está o modelo? O modelo pode residir em um arquivo local, em um serviço, em tabelas dimensionais ou em metadados da aplicação.
  3. Quem executa a consulta? Cliente, servidor de BI, gateway e banco assumem cargas diferentes conforme o modo de conexão.
  4. Onde ficam os artefatos? Consultas, métricas, painéis, permissões e agendas de atualização requerem persistência e backup próprios.

5. Power BI: Desktop, Service, gateway e Report Server

5.1 Power BI Desktop

O Power BI Desktop é um cliente de autoria. A aquisição começa em Home → Get data. O conector lê a fonte e o Power Query registra etapas de transformação. Após a transformação, o modo de armazenamento determina onde o dado consultado pelo visual ficará disponível.

ModoLocal dos dadosExecução ao interagirAtualização
ImportCópia comprimida no modelo semânticoConsulta ao modelo em memóriaRefresh recarrega a cópia
DirectQueryDados permanecem na fonteConsultas são enviadas à fonteVisuais consultam o estado corrente
CompositeCombinação de Import, DirectQuery e agregaçõesDepende da tabela e da medidaCombina refresh e consulta pass-through
Live connectionModelo semântico externoConsultas seguem para o modelo publicadoGerida no sistema que hospeda o modelo

O arquivo .pbix registra consultas do Power Query, relacionamentos, medidas DAX, formatação e páginas do relatório. No modo Import, o arquivo também inclui a cópia de dados do modelo. O modelo criado no Desktop utiliza tecnologia tabular do Analysis Services.

5.2 Power BI Service

A publicação envia o relatório e o modelo semântico para um workspace no Power BI Service. Modelos Import são carregados na capacidade do serviço e dependem de refresh para incorporar alterações da fonte. Modelos DirectQuery enviam consultas à fonte quando os usuários interagem com os visuais. Modelos compostos podem combinar os dois comportamentos.

Quando a fonte está em uma rede privada, o on-premises data gateway estabelece uma ponte de saída entre essa rede e o serviço. A credencial e o mapeamento da fonte são configurados no Service. O gateway encaminha refresh e consultas DirectQuery sem exigir a exposição pública do banco. Fontes de nuvem diretamente acessíveis podem dispensar o gateway, mantendo a configuração de credenciais no serviço.

5.3 Power BI Report Server

O Power BI Report Server é um produto on-premises para hospedar e administrar relatórios. Ele utiliza uma edição compatível do Power BI Desktop para Report Server, mantém catálogo e agendas na infraestrutura da organização e alcança fontes pela rede disponível ao servidor. Seu ciclo de atualização e sua matriz de fontes e recursos diferem do Power BI Service. Em uma discussão arquitetural, a expressão “Power BI Server” deve ser substituída pelo destino preciso: Power BI Service ou Power BI Report Server.

6. Grafana como plataforma de consumo analítico

Grafana organiza visualizações em dashboards compostos por painéis. Cada data source representa uma conexão com um backend que mantém os dados, como PostgreSQL, Prometheus, Loki ou um serviço de nuvem. O editor específico do plugin formula a consulta. Para fontes SQL usuais, o servidor Grafana usa o data source proxy e mantém conexões durante a execução.

O servidor Grafana possui um banco de aplicação para usuários, fontes configuradas, dashboards, organizações, alertas e outros metadados. A instalação local utiliza SQLite por padrão; ambientes de produção e alta disponibilidade normalmente empregam PostgreSQL ou MySQL. Esse banco de aplicação cumpre função distinta das fontes consultadas pelos painéis.

Casos de BI podem ser implementados no Grafana quando o consumo exige SQL, filtros, séries temporais, painéis operacionais e alertas. A modelagem do dado de negócio permanece uma responsabilidade da fonte ou de uma camada semântica anterior. A frequência de atualização e o auto-refresh dos painéis transferem carga para o servidor Grafana e para os backends.

7. Metabase e a arquitetura real da disciplina

O projeto metabase-olist possui um serviço de aplicação Metabase e um serviço PostgreSQL no Railway. O PostgreSQL contém bancos lógicos distintos. O banco metabase armazena contas, coleções, perguntas, dashboards, configurações e metadados sincronizados. O banco olist armazena as tabelas analíticas. Essa separação permite tratar backup e disponibilidade de cada responsabilidade de maneira explícita.

Quando o estudante cria uma pergunta no construtor visual, o Metabase representa a operação em sua linguagem de consulta e o processador a traduz para SQL do driver. Quando utiliza o editor SQL, a consulta é enviada ao banco conectado. Definição, nome, visualização e localização da pergunta ficam registrados no banco de aplicação. O resultado é obtido do Olist a cada execução, salvo quando existe uma política de cache ou persistência configurada.

7.1 Perguntas salvas como relações reutilizáveis

O editor SQL permite referenciar uma pergunta ou modelo salvo com a sintaxe {{#ID-nome}}. Ao digitar {{#, o autocomplete pesquisa artefatos da mesma conexão. Na execução, o Metabase substitui a referência pela consulta correspondente entre parênteses. Esse mecanismo permitirá que uma dimensão salva seja usada na construção do fato.

WITH dim_cliente AS {{#123-a02-g03-02-dim-cliente-scd2}}
SELECT *
FROM dim_cliente
WHERE is_current = true;

O número 123 é ilustrativo. Durante a atividade, digite o início do nome e escolha a pergunta correta no autocomplete. Uma consulta SQL salva também pode ser convertida em model por … → Turn this into a model quando a permissão da coleção disponibiliza essa ação. A referência SQL funciona com perguntas e models.

9. Data Warehouse, data mart, data lake, lakehouse e data mesh

Data Warehouse descreve uma arquitetura de dados integrados, históricos e preparados para análise. Um data mart é um recorte orientado a uma área ou processo. Data lake concentra dados em formatos variados e preserva flexibilidade de armazenamento. Lakehouse acrescenta formato tabular, transações, metadados e mecanismos de consulta analítica sobre storage de lake.

Data mesh trata principalmente de propriedade e organização. Seus princípios incluem responsabilidade orientada por domínio, dados como produto, plataforma self-service e governança federada. Um domínio de Pagamentos pode publicar um produto de dados com contrato, qualidade, documentação e controle de acesso. Esse produto pode ser fisicamente entregue como tabelas de warehouse, arquivos de lakehouse, tópicos de eventos ou APIs.

A modelagem dimensional resolve outro problema: organizar dados para consulta consistente. Um produto de dados em uma organização data mesh pode publicar fato_pagamento e reutilizar dim_cliente e dim_data conformadas. A matriz de barramento funciona como instrumento de coordenação entre processos e domínios.

10.1 Identidade do cliente

customer_id aparece uma vez na tabela de clientes e corresponde à ocorrência de cliente usada no pedido. customer_unique_id representa a pessoa identificada ao longo de múltiplos pedidos. Há 96.096 valores únicos, dos quais 2.997 aparecem em mais de uma ocorrência de pedido. A modelagem de cliente precisa escolher conscientemente qual dessas entidades representa.

10.2 Geolocalização e muitos-para-muitos

olist_geolocation possui múltiplas coordenadas para um mesmo prefixo postal. Uma junção direta entre clientes e geolocalização pelo prefixo replica clientes. Uma dimensão geográfica pode escolher uma coordenada representativa, como a mediana por prefixo, ou preservar a multiplicidade por meio de uma ponte com regra de ponderação. O requisito do mapa determina a decisão.

11. Fundamentos da modelagem dimensional

11.1 Processo e grão

O processo de negócio identifica o evento ou estado observado. O grão declara o significado de cada linha da tabela fato. A frase “uma linha por pedido” conduz a medidas diferentes de “uma linha por item do pedido”. A declaração precede o SQL e permanece anexada ao artefato como documentação.

11.2 Fatos e dimensões

Tabelas fato armazenam eventos mensuráveis e chaves para dimensões. Tabelas dimensão armazenam atributos descritivos utilizados para filtrar, agrupar e rotular. O lado “muitos” da relação costuma ser o fato; o lado “um” costuma ser a dimensão. Medidas devem ser avaliadas quanto à aditividade: preço e frete podem ser somados no grão de item; percentuais e médias exigem numerador e denominador ou recomputação no grão consultado.

11.3 Chave natural e chave substituta

A chave natural vem do sistema de origem, como product_id. A chave substituta é gerada no warehouse e desacopla o modelo analítico da chave operacional. Ela também permite múltiplas versões da mesma chave natural em SCD Tipo 2. Neste laboratório, ROW_NUMBER gera chaves substitutas determinísticas para um snapshot completo. Um pipeline incremental de produção empregaria sequência/identity, tabela de lookup e operação de upsert.

11.4 Estrela e snowflake

O esquema estrela liga o fato diretamente a dimensões relativamente desnormalizadas. Ele reduz o número de junções e apresenta uma superfície mais simples à ferramenta de BI. Snowflake normaliza partes das dimensões, criando caminhos adicionais, por exemplo produto → categoria → departamento. A normalização pode ser adequada quando hierarquias são reutilizadas e governadas de forma independente; o custo é maior complexidade de consulta e de propagação de filtros.

No Olist, 252 clientes apresentam mais de uma localização observada e 39 mudam de estado. Uma análise histórica por estado de compra requer SCD Tipo 2. A dimensão precisa de sk_cliente, valid_from, valid_to e is_current. A associação do fato utiliza a chave natural e a data do evento.

11.6 Matriz de barramento

A matriz de barramento dispõe processos nas linhas e dimensões conformadas nas colunas. Ela registra oportunidades de integração e expõe divergências. No Olist, os processos Pedidos, Itens, Pagamentos e Avaliações compartilham Cliente e Data. A dimensão Data assume papéis distintos: compra, aprovação, envio, entrega, prazo estimado e criação da avaliação.

13.2 View em ambiente gravável

Em um warehouse de desenvolvimento com DDL autorizado, o mesmo SELECT pode ser publicado como view. Essa operação deve ocorrer por migração ou pipeline administrado, fora do editor da instância compartilhada.

CREATE SCHEMA IF NOT EXISTS bi_dev;

CREATE OR REPLACE VIEW bi_dev.dim_vendedor AS
SELECT
  row_number() OVER (ORDER BY seller_id)::bigint AS sk_vendedor,
  seller_id,
  seller_zip_code_prefix,
  seller_city,
  seller_state
FROM public.olist_sellers;

GRANT SELECT ON bi_dev.dim_vendedor TO role_bi_readonly;

Esse DDL é uma referência para um warehouse administrado. Não o execute no Metabase compartilhado, cuja conexão Olist possui somente leitura.

Views executam a consulta ao serem lidas. Tabelas ou materialized views introduzem persistência e exigem estratégia de carga, atualização, observabilidade e recuperação. A escolha pertence à arquitetura de dados, não à ferramenta de visualização.

SQL 02 — dim_data 
WITH limites AS (
  SELECT
    min(order_purchase_timestamp)::date AS data_min,
    max(order_purchase_timestamp)::date AS data_max
  FROM olist_orders
)
SELECT
  to_char(cal.dia, 'YYYYMMDD')::integer AS sk_data,
  cal.dia::date AS data,
  extract(year FROM cal.dia)::integer AS ano,
  extract(quarter FROM cal.dia)::integer AS trimestre,
  extract(month FROM cal.dia)::integer AS mes_numero,
  to_char(cal.dia, 'YYYY-MM') AS ano_mes,
  extract(day FROM cal.dia)::integer AS dia_mes,
  extract(isodow FROM cal.dia)::integer AS dia_semana_numero,
  trim(to_char(cal.dia, 'TMDay')) AS dia_semana_nome,
  (extract(isodow FROM cal.dia) IN (6, 7)) AS fim_de_semana
FROM limites
CROSS JOIN LATERAL generate_series(
  limites.data_min,
  limites.data_max,
  interval '1 day'
) AS cal(dia)
ORDER BY cal.dia;

15. Atividade 3 — Dimensão cliente SCD Tipo 2

Contrato: cada linha representa uma versão de localização de customer_unique_id. valid_from é inclusivo e valid_to é exclusivo. A última versão possui valid_to vazio e is_current = true.

15.1 Comparação com SCD Tipo 1

Uma dimensão Tipo 1 pode selecionar a observação mais recente de cada cliente e produzir uma linha por chave natural. Esse desenho responde perguntas segundo a localização corrente observada no dataset.

SQL 03A — dim_cliente tipo 1 
WITH observacoes AS (
  SELECT
    c.customer_unique_id,
    c.customer_zip_code_prefix,
    c.customer_city,
    c.customer_state,
    o.order_purchase_timestamp,
    row_number() OVER (
      PARTITION BY c.customer_unique_id
      ORDER BY o.order_purchase_timestamp DESC, c.customer_id DESC
    ) AS ordem_recente
  FROM olist_customers AS c
  JOIN olist_orders AS o
    ON o.customer_id = c.customer_id
)
SELECT
  row_number() OVER (ORDER BY customer_unique_id)::bigint AS sk_cliente,
  customer_unique_id,
  customer_zip_code_prefix,
  customer_city,
  customer_state
FROM observacoes
WHERE ordem_recente = 1;

15.2 Construção da versão SCD Tipo 2

A consulta ordena observações, compara a localização com LAG, marca o início de cada versão, acumula a marca para formar segmentos e calcula os intervalos de validade. Essa reconstrução é possível porque cada customer_id se associa a um pedido com data de compra.

  1. Abra New → SQL query, selecione Olist e cole o SQL 03B.
  2. Clique em Run. Localize as colunas sk_cliente, versao, valid_from, valid_to e is_current.
  3. Clique em Save, use A02_GNN_02_DIM_CLIENTE_SCD2 e selecione a coleção do grupo.
SQL 03B — dim_cliente SCD2 
WITH observacoes_base AS (
  SELECT
    c.customer_unique_id,
    c.customer_id,
    c.customer_zip_code_prefix,
    c.customer_city,
    c.customer_state,
    o.order_purchase_timestamp AS observado_em,
    concat_ws(
      '|',
      c.customer_zip_code_prefix::text,
      c.customer_city,
      c.customer_state
    ) AS assinatura_localizacao
  FROM olist_customers AS c
  JOIN olist_orders AS o
    ON o.customer_id = c.customer_id
),
comparadas AS (
  SELECT
    *,
    lag(assinatura_localizacao) OVER (
      PARTITION BY customer_unique_id
      ORDER BY observado_em, customer_id
    ) AS assinatura_anterior
  FROM observacoes_base
),
marcadas AS (
  SELECT
    *,
    CASE
      WHEN assinatura_anterior IS NULL THEN 1
      WHEN assinatura_localizacao <> assinatura_anterior THEN 1
      ELSE 0
    END AS inicio_versao
  FROM comparadas
),
numeradas AS (
  SELECT
    *,
    sum(inicio_versao) OVER (
      PARTITION BY customer_unique_id
      ORDER BY observado_em, customer_id
      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    )::integer AS versao
  FROM marcadas
),
periodos AS (
  SELECT
    customer_unique_id,
    versao,
    min(observado_em) AS valid_from,
    max(customer_zip_code_prefix) AS customer_zip_code_prefix,
    max(customer_city) AS customer_city,
    max(customer_state) AS customer_state
  FROM numeradas
  GROUP BY customer_unique_id, versao
),
com_fim AS (
  SELECT
    *,
    lead(valid_from) OVER (
      PARTITION BY customer_unique_id
      ORDER BY versao
    ) AS valid_to
  FROM periodos
)
SELECT
  row_number() OVER (
    ORDER BY customer_unique_id, versao
  )::bigint AS sk_cliente,
  customer_unique_id,
  versao,
  customer_zip_code_prefix,
  customer_city,
  customer_state,
  valid_from,
  valid_to,
  (valid_to IS NULL) AS is_current
FROM com_fim
ORDER BY customer_unique_id, versao;

19. Fanout, CROSS JOIN e drill-across

19.1 Demonstração do fanout entre fatos

Itens e pagamentos possuem relação um-para-muitos com pedido. Uma junção direta por order_id produz o produto entre as ocorrências de cada pedido. No conjunto real, 112.650 itens e 103.886 pagamentos geram 117.601 linhas combinadas. O valor de itens cresce de R$ 15.843.553,24 para R$ 16.566.543,85; pagamentos crescem de R$ 16.008.872,12 para R$ 20.308.134,71.

SQL 08 — evidência do fanout 
WITH juncao_direta AS (
  SELECT
    count(*) AS linhas_apos_juncao,
    sum(i.price + i.freight_value) AS itens_repetidos,
    sum(p.payment_value) AS pagamentos_repetidos
  FROM olist_order_items AS i
  JOIN olist_order_payments AS p
    ON p.order_id = i.order_id
),
itens_corretos AS (
  SELECT
    count(*) AS linhas_itens,
    sum(price + freight_value) AS valor_itens
  FROM olist_order_items
),
pagamentos_corretos AS (
  SELECT
    count(*) AS linhas_pagamentos,
    sum(payment_value) AS valor_pagamentos
  FROM olist_order_payments
)
SELECT *
FROM juncao_direta
CROSS JOIN itens_corretos
CROSS JOIN pagamentos_corretos;

19.2 CROSS JOIN para uma grade completa

CROSS JOIN produz todas as combinações entre dois conjuntos. No relatório mensal por UF, ele pode construir uma grade de meses e estados para que combinações sem pedido apareçam com zero. O custo cresce pelo produto das cardinalidades; os domínios devem ser delimitados antes do cruzamento.

SQL 09 — meses × UFs 
WITH meses AS (
  SELECT DISTINCT
    date_trunc('month', order_purchase_timestamp)::date AS mes
  FROM olist_orders
),
ufs AS (
  SELECT DISTINCT customer_state AS uf
  FROM olist_customers
),
grade AS (
  SELECT meses.mes, ufs.uf
  FROM meses
  CROSS JOIN ufs
),
observado AS (
  SELECT
    date_trunc('month', o.order_purchase_timestamp)::date AS mes,
    c.customer_state AS uf,
    count(*) AS pedidos
  FROM olist_orders AS o
  JOIN olist_customers AS c
    ON c.customer_id = o.customer_id
  GROUP BY 1, 2
)
SELECT
  grade.mes,
  grade.uf,
  coalesce(observado.pedidos, 0) AS pedidos
FROM grade
LEFT JOIN observado
  ON observado.mes = grade.mes
 AND observado.uf = grade.uf
ORDER BY grade.mes, grade.uf;

O dataset possui 25 meses de compra e 27 UFs de cliente; a grade completa possui 675 linhas antes do LEFT JOIN.

19.3 Drill-across entre fatos

Drill-across agrega fatos separados pelo mesmo conjunto de dimensões conformadas e alinha os resultados agregados. A operação abaixo compara valor de itens e pagamentos por mês de compra e estado histórico do cliente. Cada fato é agregado antes da junção.

  1. Abra uma consulta SQL e insira referências para fato_item, fato_pagamento e dim_cliente.
  2. Cole o restante do SQL 10.
  3. Execute e confira as colunas valor_itens, valor_pagamentos e diferenca.
  4. Salve como A02_GNN_06_DRILL_ACROSS_MES_UF.
SQL 10 — drill-across 
WITH fato_item AS {{#ID_FATO_ITEM}},
fato_pagamento AS {{#ID_FATO_PAGAMENTO}},
dim_cliente AS {{#ID_DIM_CLIENTE_SCD2}},
itens_agregados AS (
  SELECT
    (fi.sk_data_compra / 100)::integer AS sk_mes,
    dc.customer_state AS uf,
    sum(fi.valor_item) AS valor_itens
  FROM fato_item AS fi
  JOIN dim_cliente AS dc
    ON dc.sk_cliente = fi.sk_cliente
  GROUP BY 1, 2
),
pagamentos_agregados AS (
  SELECT
    (fp.sk_data_compra / 100)::integer AS sk_mes,
    dc.customer_state AS uf,
    sum(fp.valor_pagamento) AS valor_pagamentos
  FROM fato_pagamento AS fp
  JOIN dim_cliente AS dc
    ON dc.sk_cliente = fp.sk_cliente
  GROUP BY 1, 2
)
SELECT
  coalesce(i.sk_mes, p.sk_mes) AS sk_mes,
  coalesce(i.uf, p.uf) AS uf,
  round(i.valor_itens, 2) AS valor_itens,
  round(p.valor_pagamentos, 2) AS valor_pagamentos,
  round(p.valor_pagamentos - i.valor_itens, 2) AS diferenca
FROM itens_agregados AS i
FULL OUTER JOIN pagamentos_agregados AS p
  ON p.sk_mes = i.sk_mes
 AND p.uf = i.uf
ORDER BY sk_mes, uf;

Uma dimensão é conformada quando apresenta significado, conteúdo e regras compatíveis entre processos. Igualdade de nome não garante conformidade. Chaves, política histórica, valores desconhecidos, traduções e hierarquias precisam ser coordenados.
