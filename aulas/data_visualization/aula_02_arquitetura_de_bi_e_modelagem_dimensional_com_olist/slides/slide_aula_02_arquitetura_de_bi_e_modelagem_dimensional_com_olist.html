Modelagem dimensional · 9h25–9h30

Grão responde: o que exatamente uma linha representa?

Definição operacional Imagine uma etiqueta anexada a cada linha: “esta linha representa ______”. A frase completa define o grão e fixa o nível de detalhe da tabela.
Pedidocada linha representa um pedido identificado por order_id.
Itemcada linha representa um item numerado dentro de um pedido.
Pagamentocada linha representa uma ocorrência sequencial de pagamento.

O grão define quais colunas podem coexistir, quais medidas podem ser somadas e quais junções preservam o significado de uma linha.

Exemplo guiado · 9h30–9h35

Uma compra pode produzir quantidades diferentes de linhas

Considere o pedido didático PED-042, composto por três itens e pago em duas ocorrências.

TabelaGrão declaradoLinhas de PED-042Chave candidata
ordersum pedidoPED-042order_id
order_itemsum item do pedidoPED-042/01, /02, /03order_id + order_item_id
paymentsuma ocorrência de pagamentoPED-042/01, /02order_id + payment_sequential
Previsão antes do SQLUnir itens e pagamentos diretamente pelo pedido produz 3 × 2 = 6 linhas. O crescimento é consequência da mistura de dois grãos.
Procedimento · 9h35–9h40

Defina e teste o grão antes de selecionar colunas

1. Pergunta“Qual é o valor bruto dos itens, com frete, por categoria?”
2. ProcessoVenda de itens, pois a categoria pertence ao produto.
3. Frase“Cada linha representa um item dentro de um pedido.”
4. Chaveorder_id + order_item_id.
5. TesteLinhas = chaves distintas; junções preservam a quantidade esperada.

Se uma coluna descreve outro nível de detalhe, ela deve ser agregada previamente, movida para outra tabela ou tratada em outro conjunto de ocorrências.

Chaves · 9h45–9h48

Cada tipo de chave cumpre uma função no modelo

TermoFunçãoExemplo Olist
Candidatacombinação mínima que identifica uma linha no grãoorder_id + order_item_id
Primáriachave candidata escolhida para identificar a linhaproduct_id na dimensão

sk abrevia surrogate key, ou chave substituta. A chave natural preserva a correspondência com a origem; a substituta controla a identidade analítica.

Medidas · 9h48–9h50

Aditividade define em quais direções uma medida pode ser somada

AditivaPode ser somada nas dimensões compatíveis. Exemplo: preço do item por produto, cliente ou mês.
SemiaditivaPode ser somada em algumas dimensões, mas não em outra. Exemplo clássico: saldo entre contas, não entre datas.
Não aditivaTaxa, média e percentual precisam ser recomputados a partir de seus componentes.
Regra de implementaçãoPara uma taxa, preserve numerador e denominador. A média das médias pode atribuir o mesmo peso a grupos de tamanhos diferentes.

Desnormalizar reúne atributos relacionados na mesma dimensão. Snowflake os separa em tabelas quando hierarquias precisam de gestão independente.

Laboratório · Objetos do banco

View não materializada guarda a consulta; materializada guarda o resultado

View comum
  1. guarda a definição do SELECT;
  2. não mantém cópia própria das linhas;
  3. recalcula quando é lida;
  4. reflete os dados consultáveis naquele momento.
View materializada
  1. guarda as linhas calculadas;
  2. ocupa disco e pode receber índices;
  3. lê o resultado persistido;
  4. exige REFRESH MATERIALIZED VIEW.
Decisão do laboratórioDimensões e fatos serão views comuns em bi_aula02. Como o editor do Metabase não oferece suporte oficial a DDL, o professor deve testar a execução antes da aula e manter uma migração administrativa como alternativa.

Atividade 2 · 10h30–10h38

  1. Abra New → SQL query e selecione Olist — DDL Aula 02.
  2. Troque gnn pelo código do grupo.
  3. Use generate_series entre a menor e a maior compra.
  4. Execute o CREATE OR REPLACE VIEW com Run.

CREATE OR REPLACE VIEW bi_aula02.gnn_dim_data AS WITH limites AS ( SELECT min(order_purchase_timestamp)::date AS data_min, max(order_purchase_timestamp)::date AS data_max FROM public.olist_orders ) SELECT to_char(dia, 'YYYYMMDD')::integer AS sk_data, dia::date AS data FROM limites CROSS JOIN LATERAL generate_series( data_min, data_max, interval '1 day' ) AS c(dia);

generate_series cria uma sequência contínua de datas. sk_data é a chave substituta usada pelos fatos para referenciar cada dia.

Fanout e cardinalidade · 11h20–11h26

Fanout é a multiplicação de linhas causada pela junção

Cardinalidade descreve quantas linhas podem se relacionar. Dois lados “muitos” combinados pelo pedido repetem as medidas de ambos.

ConjuntoLinhasValor corretoApós itens × pagamentos
Itens112.650R$ 15.843.553,24R$ 16.566.543,85
Pagamentos103.886R$ 16.008.872,12R$ 20.308.134,71
Junção direta117.601 combinações por order_id
DiagnósticoUm pedido com 3 itens e 2 pagamentos gera 6 linhas. Cada medida é repetida pela cardinalidade do outro fato. A solução analítica agrega cada fato no grão comum antes de alinhá-los.
CROSS JOIN · 11h26–11h32

O produto cartesiano cria uma grade analítica completa

WITH meses AS (...), ufs AS (...), grade AS ( SELECT mes, uf FROM meses CROSS JOIN ufs ), observado AS (...) SELECT grade.mes, grade.uf, coalesce(observado.pedidos, 0) AS pedidos FROM grade LEFT JOIN observado USING (mes, uf);

Aplicação

Mostrar meses sem pedido com valor zero e preservar comparações entre UFs.

Controle

O total de linhas da grade é o produto das cardinalidades. Filtre domínios antes do cruzamento.
